# Pre-candidate boundary-analysis supplement

Status: **Proposed analysis supplement. Review and commit before v3 candidate
measurements. No v3 candidate data have been generated by these tools.**

## Source-derived settings versus new analysis decisions

The committed `PHYSICAL_V3_CONTRACT.md` and `run_v3.py` at `57db318` declare
q = {0,1,2}, application lifetime = {3,6,9,12,20} seconds, five repetitions,
a five-second candidate pulse, a 250 ms clock bound and a 1000 ms
request-classification margin. The supplied Stage-1 plan uses those settings and
P0 (`physical_v3_broker_only`) only: 15 cells / 75 target rows. It is not a plan
for new hardware operation in this package.

The following are explicit **new analysis conventions**, not assertions already
proved by the old contract or code:

* Recalculate L = `pre_service_at_ms - expires_at_ms`. Preserve the supplied
  lateness too. A mismatch larger than 0.01 ms invalidates that row's consistency;
  do not repair it silently or use it in the headline chart.
* Classify L < -1000 as on time, L > +1000 as late, and the entire inclusive
  [-1000,+1000] interval as boundary. This reports the conservative margin,
  **not** the claim that a +500 ms request meets the strict application deadline.
* A single receipt must be observed with `received_at_ms + 250 < expires_at_ms`.
  Clock assumptions need a separately validated runner/event record.
* Check IDs, repetitions, counts, null values, finite values, plan membership,
  duplicate IDs/rows and count-versus-timestamp consistency. Preserve invalid
  and unresolved cases; never pick the favorable duplicate.
* Do not promote an upstream unresolved/invalid event-audit status to success.
* `receipt_to_pre_service_ms` includes ingress-probe, dispatch, condition and
  queue delays. It is **not** pure queue residence unless separately measured.
  Small negative receipt-to-marker observations remain recorded, not clamped.

## Input schema

CSV rows use the existing measurement-v3 column terminology, plus `rep` supplied
by the eventual runner. Required columns:

```
command_id,policy,queue_depth,ttl_s,rep,expires_at_ms,
receipt_count,received_at_ms,pre_service_count,pre_service_at_ms,
pre_service_lateness_ms,endpoint_on_transition_count,endpoint_on_at_ms,
rejected_count,unmatched_endpoint_on_count,unmatched_endpoint_off_count,outcome
```

Keep missing timestamps empty. Do not encode absent execution as zero latency.
Optional fields (including `test` and raw-event provenance) are retained.
`fixture_only=true` requires the explicit synthetic-analysis mode.

This tool analyzes one planned study at a time. It does not silently rename v2
columns or combine devices, studies, runs or repetitions. Future policy studies
need a separate reviewed plan. It never auto-selects favorable policy cells from
a boundary result.

## Denominators and display

Each cell reports planned, observed, valid, on-time, late, boundary, rejected,
invalid/unresolved, and missing counts. `late_fraction_valid_executed` uses only
late + on-time executed rows; boundary rows are explicitly excluded from that
ratio. It is undefined when there are no assessable executions.

The main heatmap masks incomplete/error-bearing cells rather than painting them
as zero violations. Complete cells print the late/assessable count and boundary
count. A cell with five boundary rows therefore has no defined late fraction,
not a zero failure rate. All descriptive points and invalid rows remain in CSV.

Latency summaries use n, mean, sample SD, median, min and max. SD is null for n<2.
No confidence interval or population reliability claim is manufactured from five
fixed-workflow repetitions. A policy's lower observed mean in this study is not
an isolated overhead measurement.

## Example — offline only, when a genuine future input exists

```
python -m v3_analysis_optical.boundary --input PATH_TO_REVIEWED_V3_TRIALS.csv --output v3_analysis_optical/_output/boundary-analysis-01
```

The CLI exits nonzero for incomplete/invalid study coverage but writes diagnostic
outputs when possible. Unknown schemas/missing columns are rejected outright.
Inputs and the analysis plan are hashed. Outputs are exclusive new directories.

## What this does not prove

This is a consistency-aware **CSV analysis**, not an independent raw-event
attribution validator. A correct subtraction and a zero count do not prove
causality or absence of effects. The raw-event auditor and live runner must
independently establish those facts. The current v3 classifier must be corrected
before its CSV can support the candidate study; see INTEGRATION_BLOCKERS.md.
